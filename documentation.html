1. Project Background & Target System

This accessibility assessment was conducted as part of the RabTech Academy Internship (Task 03: Semantic HTML5 & Accessible Component Architecture). The objective is to audit the digital accessibility posture of a public government portal, record baseline findings, and establish a professional accessibility management dashboard.

Four core principles: Perceivable, Operable, Understandable, and Robust (POUR).

2. Testing Methodology: Automated vs. Manual

A balanced, enterprise accessibility audit combines automated scans with rigorous manual testing. Automated auditing tools reliably flag deterministic structural violations, but cannot evaluate context, reading order, screen reader pronunciation, or user task flow.

Automated Lighthouse Scanning (30%–40% Coverage)

  • Evaluates color contrast ratios programmatically against WCAG 1.4.3 formulas.
  • Detects missing required parent/child ARIA roles (e.g., role="listitem" without role="list").
  • Validates basic semantic nesting and missing alternative text on images.
  • Flags interactive elements with insufficient touch targets or duplicate link names.

Manual Verification Protocol (60%–70% Coverage)

  • Keyboard Navigation: Verify all interactive elements are reachable via Tab and navigable via Shift+Tab.
  • Focus Visibility: Ensure high-contrast visual focus indicators meet WCAG 2.4.7 and 2.4.11 criteria.
  • Screen Reader Auditing: Test with NVDA (Windows), JAWS, or VoiceOver for logical reading order and announcements.
  • Dynamic State Changes: Verify modals trap focus correctly and status updates announce politely via aria-live.

3. Baseline Findings & Technical Analysis

The recorded Lighthouse audit of India.gov.in produced 5 initial baseline findings across 3 WCAG principles. Below is the technical breakdown:

  1. 01

    WEB-001: ARIA Role Parent Relationship (WCAG 2.1 — 1.3.1 Info and Relationships)

    Component: Top Bar Service List (div#topBarServiceList).
    Root Cause: Elements assigned role="listitem" were not contained within an element with role="list".
    Remediation: Replace customized ARIA divs with native semantic <ul> and <li> elements, or provide the required role="list" container.

  2. 02

    WEB-002: Insufficient Color Contrast (WCAG 2.1 — 1.4.3 Contrast Minimum)

    Component: Header Overlay Text ('Avail online Services & Save time').
    Root Cause: Text overlay lacked sufficient contrast ratio against the background imagery or banner gradient.
    Remediation: Darken text or apply a solid background scrim to achieve at least 4.5:1 contrast for normal text.

  3. 03

    WEB-003: List Items Missing a Valid Parent (WCAG 2.1 — 1.3.1 Info and Relationships)

    Component: Website List Components.
    Root Cause: List items (<li>) were rendered without direct <ul>, <ol>, or <menu> parent elements.
    Remediation: Enclose all list items within proper semantic list container tags.

  4. 04

    WEB-004: Touch Target Size and Spacing (Needs Verification / Best Practice)

    Component: Interactive Controls.
    Root Cause: Flagged controls had active touch targets under 48x48 CSS pixels or insufficient spacing.
    Remediation: Expand hit area padding and ensure at least 8px separation between adjacent clickable controls.

  5. 05

    WEB-005: Repeated Links Require Review (WCAG 2.1 — 2.4.4 Link Purpose)

    Component: Repeated Links.
    Root Cause: Multiple links on the page share identical accessible names but navigate to different destinations.
    Remediation: Provide unique, context-descriptive link labels or use visually hidden text to disambiguate destinations.

5. Accessible Component Architecture (Task 03)

This dashboard architecture implements best practices for semantic HTML5 and accessible web components:

Semantic Document Landmarks

  • <header>: Top-level branding and global application controls.
  • <nav>: Primary and sidebar navigation with explicit aria-label and aria-current="page".
  • <aside>: Responsive sidebar navigation landmark.
  • <main id="main">: Primary content landmark accessible via skip link.
  • <footer>: Consistent application footer with quick links and attribution.

Accessible Component Architecture

  • Skip-to-Main Link: First focusable element on every page for keyboard and screen reader efficiency.
  • Native Modal Dialogs: Native <dialog> with focus trap, Escape key listener, and focus restoration to trigger elements.
  • Accessible Forms: Semantic <fieldset>, <legend>, explicit labels, error summary box with role="alert", and live success banners.
  • W3C Validated HTML5: Strict adherence to HTML5 standards, zero syntax errors, and zero redundant ARIA roles.
